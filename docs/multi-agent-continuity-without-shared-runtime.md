# Multi-agent continuity without a shared runtime

**How we kept two agents in sync for months using nothing but files, and what it cost us.**
两个互不可见的 agent 运行时，仅靠落在磁盘上的日志维持连续性——四个月的取舍、踩过的坑、以及六个可以直接抄走的做法。

> 这篇是对 DeepSeek 的 Super-agent 研究原型 / 技术文章的**独立实践回应**，不是对它的改进建议，也不代表它的立场。
> 我们走的是另一条路线。路线不同，代价也不同——第 5 节把我们不如他们的地方全部列出来了，请先读那一节再判断这篇值不值得信。

---

## TL;DR

When one human can only look after a few agent sessions, the bottleneck stops
being model intelligence and becomes **human attention**. The usual answer is a
stronger global memory for the router. Our answer was the opposite: **do not
build the router's global memory at all — externalise it into append-only files
that can be searched, diffed and replayed.**

Router restarts, context compresses, the model is swapped, the harness is
replaced — the state survives all of it. What we lost: transactions, idempotency
and ordering guarantees. We do not claim this is better. We claim it is a
different trade-off, and it is worth knowing it exists.

## 1. 他们问的问题

DeepSeek Harness 团队的 `dsh-superagent-prototype`（MIT，2026-10 末公开）提出的
核心问题是：当一个人同时只能照看有限个 agent 会话时（经验值 3~5 个），限制生产力
的也许不再是模型的智商，而是人的注意力。

它的结构是**一个运行时里的两层**：

- **Router** —— 轻模型、不挂执行工具、持有全局上下文，负责调度与对人说话；
- **Worker** —— 强模型、独立会话与目录，负责隔离执行。

并在文档里承认了一个它自己没解掉的权衡（**二手转述**，官方公众号原文我们未取到全本，
其仓库 `docs/` 下的哲学/执行/面板/架构四篇是我们实际读到的）：

> 切分粒度越细，Router 的吞吐越高，但分片之间的记忆与上下文连续性越低。
> **在全局记忆问题被解决之前，这个权衡始终存在。**

这句是整篇研究里最诚实的一句，也是我们唯一能直接回答的一句。

---

## 2. 我们为什么会在同一条轨道上

我们的问题是同一个，但起点不同：不是一个运行时里的两层，而是**两个完全独立的运行时**
（各自的进程、配置、记忆、技能、定时任务，甚至不同模型）。它们之间唯一共享的东西，
是文件系统。

没有 Router 持有全局上下文——因为**没有 Router**。人（也就是那位被保护注意力的老板）
是它们之间唯一共同的"上层"，而人不能被当作状态存储。

于是我们做的事不是"解决全局记忆"，而是**取消这个需求**：

| 他们 | 我们 |
|:--|:--|
| Router 用上下文维持全局连续性 | 连续性**外化成文件**：编号信件、任务台账、产出件的时间戳 |
| Router 是唯一的全局状态持有者 | 没有任何进程持有全局状态 |
| 分片间靠 Router 转述对齐 | 分片间靠**读同一批文件**对齐 |
| 上下文压缩 = 状态风险 | 压缩只丢会话内对话，状态从不进去 |

工作量上这不是免费的：每一封跨 agent 的通信都要**落盘**（不是口头转述），每一步状态变化
都要**写进台账**（不是记在心里），每次醒来要**先扫盘再判断**（不是回忆上次聊到哪）。
换来的是：Router 可以重启、可以被压缩、可以换模型、可以换 harness，而全局状态不丢。

## 3. 六条对照：他们的假设 → 我们实际观测到的 → 机制原因

下面每一条都是我们踩出来的，不是设计出来的。写法统一为「假设 / 观测 / 机制」，
不写成"我们的做法更优"——那是另一回事。

### 3.1 状态派生会过期，而假警报比漏报更贵

- **假设**（其面板文档）：一个"需要人处理"的条目，可以由存储的状态派生出来
  （最新的任务被报为 blocked/failed，且此后没有人工消息）。
- **观测**：派生值本身会过期。对方的回信早已落盘、文件早已更新，状态字段还是旧的；
  人被问了"你要拍板什么"，而这件事其实早就定了。**每一条过期的警报，都在消耗那个本来要被保护的资源。**
- **机制**：派生值只在**写它的那一刻**正确。存储型面板缺一个字段：`as-of`。

**做法**：面板上每一条都要带三个东西——什么时候算的、依据哪条证据（文件路径/消息 id/
修改时间）、心跳本身是否在推进（否则无法判断"没更新"是没变化还是探针死了）。

### 3.2 "健康"不等于"调用成功"

- **假设**（其面板/Watchdog）：健康条目按**调用级**统计（某类操作连续失败三次才亮红灯）。
- **观测**：我们最大的故障类别不是崩溃，是**静默失效**——进程正常退出、退出码为 0、
  调度器报成功，但产出是空的、是旧的、或者口径错了。调用级健康检查对这个完全失明。
- **机制**：调用成功只证明"执行了"，不证明"有产出"。

**做法**：把健康判据从「调用成败」升级为「**产出新鲜度**」，三个判据全过才算活：
① 最新产出的修改时间在窗口内 ② 非空且规模合理（字节/行数下限）③ 内容自洽
（今天的时间戳真的在里面、必需章节真的存在）。见本文附带的 `liveness_probe.py`。

### 3.3 注意力可以契约化，而且"写短一点"不可校验

- **假设**：把原则写进哲学散文与提示词——"只在必须有人行动时才说话"。
- **观测**：提示词会漂移。同一个提示词，不同会话读到的是不同的人。人还是得读完整篇
  才知道要不要动手。
- **机制**：提示词约束的是**生成过程**；格式契约约束的是**产物**。前者不可校验，后者一条正则就行。

**做法**：给所有面向人的汇报定死形状——**第一行固定**（"需要你批准：<一句话｜无>"），
正文固定三段（做过 / 没成 / 接下来）且有字数上限，禁用内部术语裸奔。
不合格由程序判定，不靠人读。见附带的 `report_contract_check.py`。

这条的副作用要说清：格式一旦定死，**信息密度会被牺牲**——有些复杂事三段装不下，
我们因此额外维护一个"细节走长文档、汇报只给指针"的分层，多了维护成本。

### 3.4 批处理只用在机器侧是不够的

- **假设**（其批处理权衡）：把 Router 的决策攒批（例如每次决策约 1.6s 的 prefill），
  提高吞吐、降低人均打扰。
- **观测**：批处理确实在机器侧工作，但**人的队列没人管**。观察项一条条即时推送出去，
  同一个上下文被反复重建，注意力成本线性增长。
- **机制**：注意力和缓存一样，**同一个上下文里处理多件事的边际成本近零**；
  分散在不同时刻处理，每次都要重新建立上下文。

**做法**：观察类产物**不即时推送**——只攒件，统一时点批量销账。同一时刻、同一收件人、
同一主题合并成一次到达。

### 3.5 Router 一旦水平切分，"多入口共写"的坑必然出现

- **假设**（其架构文档列为 open question）：Router 未来会切分为多层/多实例。
- **观测**：我们提前撞上了。同一个 agent 有三个唤醒入口——人直接对话的主会话、
  消息触发的自动会话、定时任务会话——共用同一个工作区，**彼此不可见、无互斥**。
  实测：同一个脚本被两条会话隔两分钟各自修改，后者静默覆盖前者，没有任何报错。
- **机制**：没有"谁在写"的概念，就没有冲突检测。这和 Router 切几层无关，
  和"是否允许多个执行体写同一块地"有关。

**做法**：三段——① 定主/子（人能直接对话的那个是主，其余是子，子只做无人值守的活）；
② 投递收口（同址的信只落盘、不另起会话，把唤醒交回对方自己的门控）；
③ **单写者文件锁**（动手写生产前先取锁，拿不到就只读 + 落信，不硬干）。
僵尸锁可回收，TTL 兜底，不死锁。见附带的 `write_lock.py`。

### 3.6 成本要能分账，否则"省了注意力"是一笔糊涂账

- **假设**：他们给了订阅直通省下的相对差（约 37%），但没给总 token 账单。
- **观测**：我们也犯过同样的错——只统计总量，回答不了"这一批活省了多少人的时间、
  多花了多少钱"，也就无法判断这个取舍值不值。
- **机制**：成本必须能按**角色**（调度侧/执行侧/投机执行）分桶，否则浪费率不可测。

**做法**：按 provider/key/线路分账，且"投机执行"单独一桶。投机执行的浪费率，
正是"少打扰优先于少浪费"这个选择的价签。

## 4. 我们的做法（机制版，一段话）

两个独立运行时，各自有记忆与技能。跨运行时的通信 = **落盘的一封信**（编号、单向、
不回执类不回复），信落盘后再走一次"门铃"投递把对方唤醒。共享状态 = **一个任务台账**
（每项有状态与备注）+ **产出件的修改时间**。断言之前先扫盘核 `mtime`，因为**状态字段
一律视为可能过期**。动手写生产之前先取单写者锁。面向人的汇报走格式契约。

没有一件是新发明，组合起来的效果是：任何一个运行时挂掉、重启、被压缩、换模型，
另一个不感知，全局状态也不丢。

## 5. 他们有的我们没有（必须写的一节）

不写这节，上一节就是自吹。以下是我们**明确弱于**那个原型的地方：

| 能力 | 他们 | 我们 |
|:--|:--|:--|
| durable effect queue | 有（持久队列 + outbox receipt） | **没有**。我们是"先落盘再执行"的人肉版，靠指纹去重兜丢失 |
| 幂等与同会话有序 | 有保证 | **弱**。重跑靠指纹，不重不漏是**约定**而非**保证** |
| 暂停语义 | 有（暂停期间评估不过期、deadline 顺延） | **没有**。我们只能靠"锁 + 人工确认"近似 |
| 策略版本化 + 授权重验 | 有（Policy 版本 + Mandate 重验） | **没有**。我们靠"改规则须 owner 本人确认 + 谁改的留痕" |
| 单写者事务 | SQLite 级 | **文件锁 + 规范形复核**，弱于真正的单写者事务 |
| 权限/审计/可观测性 | 原型里也缺 | 我们同样缺，只是靠日志与台账人工兜 |

所以这篇的立论只能是：**在没有共享运行时的前提下，如何用日志化状态维持多 agent 的连续性**。
它是另一条路线，不是更好的实现。如果条件允许（同一个进程内、能接受一个中心状态存储），
他们的架构在一致性上更强。

还有两处我们没解：

- **信件丢失**：落盘 + 门铃是两步，中间失败没有原子性。我们靠"对方定时扫盘"兜底，代价是延迟。
- **规模上限**：文件多了以后，扫盘的成本随文件数线性上升，我们目前没有做索引。

## 6. 可复用清单（明天就能抄走的六条）

1. **汇报格式契约**：第一行说清要不要人动手；正文三段；有字数上限；由程序检查。
2. **产出新鲜度三判据**：新鲜 / 非空且规模合理 / 内容自洽。退出码 0 不算成功。
3. **单写者文件锁**：多入口共写之前先取锁；拿不到就只读 + 上报；TTL 兜底防死锁。
4. **投递收口**：同一地址的信只落盘，不另起会话；唤醒交回对方自己的门控。
5. **状态字段视为过期**：断言前先核证据（文件/时间戳），不核不报。
6. **按角色分账**：调度侧/执行侧/投机执行分桶计成本，否则不知道省注意力花了多少钱。

附带的三个脚本都是独立的、无外部依赖的、与具体业务无关的：

- `scripts/report_contract_check.py` —— 汇报形状检查器（首行/分段/字数/禁词）
- `scripts/liveness_probe.py` —— 静默失效三判据体检器（读 JSON spec，只读，不写产出）
- `scripts/write_lock.py` —— 单写者文件锁（flock + TTL + 僵尸回收 + 多工作台）
